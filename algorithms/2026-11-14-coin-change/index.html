零钱兑换：从最后一枚硬币推回最优解

题意和示例

给定正整数面额数组 coins 和非负目标金额 amount。每种硬币数量不限，求恰好凑出目标金额所需的最少硬币数；无法凑出时返回 -1。目标为零时，答案为零。

例如 coins = [1, 2, 5]、amount = 11，可以用 5 + 5 + 1，答案是 3。若只有面额 2，目标为 3，则返回 -1。

不要把“每次拿最大的硬币”当成通用解法：面额为 [1, 3, 4]、目标为 6 时，贪心拿到 4 + 1 + 1，但 3 + 3 只要两枚。

考查点

  • 能否把“求一个金额的答案”拆成“求更小金额的答案”。
  • 能否区分零枚硬币与不可达，而不是把整个数组初始化成零。
  • 能否解释硬币为什么可以重复使用，以及金额为什么从小到大遍历。

这是求最少数量的完全背包问题，不是统计组合数。

Java 代码

import java.util.Arrays;

class Solution {
    public int coinChange(int[] coins, int amount) {
        int unreachable = amount + 1;
        int[] dp = new int[amount + 1];
        Arrays.fill(dp, unreachable);
        dp[0] = 0;

        for (int sum = 1; sum <= amount; sum++) {
            for (int coin : coins) {
                if (coin <= sum && dp[sum - coin] != unreachable) {
                    dp[sum] = Math.min(dp[sum], dp[sum - coin] + 1);
                }
            }
        }

        return dp[amount] == unreachable ? -1 : dp[amount];
    }
}

输入按题意保证面额为正、目标非负；这里不额外实现非法输入校验。

文字推导与正确性

把最后一枚硬币拿掉

定义 dp[sum] 为凑出金额 sum 的最少硬币数。

假设最后一枚硬币是 coin，去掉它后，剩下的金额就是 sum - coin。只要这个金额能凑出，就得到一个候选答案：

dp[sum - coin] + 1

枚举所有不超过 sum 的面额，取候选答案的最小值即可。我们不需要记录硬币的排列顺序，因为这里只关心数量。

为什么初始化成 amount + 1

金额为零不需要硬币，所以 dp[0] = 0。其他状态最初均不可达。

面额都是正整数，因此任何能凑出目标金额的方案，硬币数都不会超过 amount。用 amount + 1 表示不可达，便不会与合法答案混淆；代码还显式跳过不可达前驱。

以 [1, 3, 4] 为例，金额 1 到 6 的最优值依次是 1、2、1、1、2、2。处理 6 时，最后拿 1 得到 dp[5] + 1 = 3，最后拿 3 得到 dp[3] + 1 = 2，最后拿 4 得到 dp[2] + 1 = 3，最终留下 2。

为什么递推不会漏掉最优解

对金额从小到大归纳。零金额的答案正确；处理正金额 sum 时，每个合法面额都大于零，所以前驱 sum - coin 更小，其最优值已经计算完成。

任取一个凑出 sum 的最优方案，最后总有一枚硬币。去掉它后的方案也必须最优，否则换成更少硬币的前驱方案，就能改进原方案，与最优性矛盾。

算法枚举了这枚硬币，也就覆盖了最优方案。同时，每个被采用的候选都来自可达前驱加一枚真实硬币，因此不会凭空构造答案。若没有候选，状态保持不可达。

这里的状态不限制某种面额使用几次，所以同一硬币面额可以沿递推链反复出现。不需要把金额倒序遍历；倒序是另一类限制每件物品只能用一次的背包写法中常见的处理方式。

复杂度和边界

设硬币种类数为 n，目标金额为 A。

  • 时间复杂度：O(nA)；更精确地计入数组初始化，为 O(A + nA)。
  • 额外空间：O(A)，用于状态数组。
  • amount = 0：直接由初始状态返回 0。
  • 所有面额都大于目标，或目标无法组合得到：返回 -1。
  • 面额乱序不影响结果，不需要排序；重复面额只会重复比较，不改变答案。
  • 负面额、零面额、负目标不属于本实现接受的题目输入。

大面额只参与大小比较；只有 coin <= sum 时才计算差值，因此不会因大面额而访问负下标。代码没有用 Integer.MAX_VALUE 作为哨兵，避免对该值加一溢出；不可达前驱也不会参与加法。

这份数组解法依赖目标金额能在题目规模内分配数组。若推广到接近 Java int 上限的目标，amount + 1 会溢出，内存也无法承受，不能直接套用此实现，需要重新评估输入规模和算法。

面试时忘记怎么办

先写一个反例：[1, 3, 4] 凑 6。它能提醒自己，局部拿大面额不保证全局最少。

再问：“如果知道最后一枚是什么，剩余问题是什么？”剩余金额为 sum - coin，递推式就自然出现了。

接着补齐三个细节：零金额设为零、其余设为不可达、金额从小到大计算。最后用“每个金额枚举所有面额”说明时间复杂度，用“只存每个金额的最优值”说明空间复杂度。

可以这样讲核心理由：枚举最后一枚硬币，把所有可能的最优方案归到已解决的更小金额上。

一句话总结

零钱兑换不是猜下一枚该拿多大，而是对每个金额枚举最后一枚，把可达前驱的最优值加一后取最小。
