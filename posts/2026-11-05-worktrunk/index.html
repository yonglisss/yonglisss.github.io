Worktrunk：让多个 AI 并行改代码，先把工作目录分开

两个编程助手同时处理需求，最容易乱的不是对话，而是代码现场：一个切分支，另一个还在改文件。Worktrunk 是面向并行智能体工作流的 Git 工作树管理命令行工具。本次核验时它出现在 GitHub 周热门榜上，值得看的不是“多开几个 AI”，而是怎样降低切换、查看和收尾的成本。

两个编程助手同时处理需求，最容易乱的不是对话，而是代码现场：一个切分支，另一个还在改文件。Worktrunk 是面向并行智能体工作流的 Git 工作树管理命令行工具。本次核验时它出现在 GitHub 周热门榜上，值得看的不是“多开几个 AI”，而是怎样降低切换、查看和收尾的成本。

📌 这个项目是干什么的

  • 基于 Git 原生工作树，让不同任务在各自目录中修改文件。
  • 用分支名定位工作树，不必反复记住目录路径。
  • 适合已经使用 Claude Code、Codex 等工具，需要同时处理独立需求的开发者。

它不是新的大模型，也不是替你拆任务的调度平台，而是给现有开发流程补上工作区管理。

🔍 为什么值得关注

第一，创建、切换和查看状态变成短命令。wt list 能汇总多个工作树的状态，减少逐个目录检查的机械操作。

第二，可以在创建工作树后启动编程助手，也能通过钩子执行初始化命令。对开发者更有借鉴意义的是：把准备环境变成可重复流程，而不是每次手工复制一遍。

但先别急着配置全自动合并。更稳妥的收益，是让两个边界清楚的小任务各有现场，最后仍用差异审查和测试验收。

🧪 谁适合试，怎么开始

如果平时只有一个任务在推进，原生 Git 可能已经够用。有并行需求时，再在练习仓库试一次。官方给出的安装与起步命令如下，安装需具备对应环境：

cargo install worktrunk
wt config shell install
wt switch --create feature-a
wt list

Shell 集成用于支持命令切换目录，按安装提示生效后再继续。先验证新分支和目录是否符合预期，再给两个工作树分别安排“补测试”和“修独立缺陷”，不要一上来就让它们改同一模块。

⚠️ 使用提醒

工作树分开，不等于权限隔离，也不代表合并不会冲突。开发服务器端口、数据库和外部服务仍需单独规划；官方实践文档也提供了按工作树分配端口和数据库的方案。

钩子会执行命令，启用前要检查内容。项目采用 MIT 或 Apache-2.0 双许可证，可择一遵循。本文核验了官方资料与命令示例，未实测安装，不承诺并行数量增加就能提高交付效率。
