两数之和：为什么哈希表必须先查再存？

题意和示例

给定整数数组 nums 和目标值 target，返回两个不同位置的下标，使对应元素之和等于目标值。题目保证恰好存在一组答案，返回顺序不限。

例如 nums = [2, 7, 11, 15]、target = 9，返回 [0, 1]。要求的是下标，不是 [2, 7] 这两个数值。

再看 nums = [3, 3]、target = 6：两个数值相同没有问题，只要下标不同，答案就是 [0, 1]。

考查点

  • 把“两数相加”改写为“寻找当前数的补数”。
  • 用数值到下标的映射，省掉反复扫描数组的过程。
  • 用处理顺序保证不重复使用同一个位置，而不是找到答案后再补检查。

数组没有排序条件。直接排序会打乱原下标；若采用排序加双指针，需要额外保存原位置。这里选择不改变输入的哈希表解法。

Java 代码

import java.util.HashMap;
import java.util.Map;

class Solution {
    public int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> seen = new HashMap<>();

        for (int i = 0; i < nums.length; i++) {
            int need = target - nums[i];
            Integer previous = seen.get(need);
            if (previous != null) {
                return new int[] {previous, i};
            }
            seen.put(nums[i], i);
        }

        throw new IllegalArgumentException("No valid pair");
    }
}

最后的异常只为补全方法的返回路径；满足原题“存在唯一答案”的输入不会执行到这里。代码不修改原数组。

文字推导与正确性

从枚举配对到查询补数

暴力解固定一个下标，再检查其余位置，总共需要枚举二次数量级的配对。

但当前数字确定后，另一半也就确定了：need = target - nums[i]。我们不需要重新遍历所有旧元素，只需要回答“这个值以前出现在哪里”。因此哈希表的键存数值，值存下标。

以 [2, 7, 11, 15] 为例，处理 2 时需要 7，表中没有，于是存入 2 -> 0。处理 7 时需要 2，查到下标 0，便返回 [0, 1]。

为什么先查，再存？

每轮开始时，表里只允许存在当前下标之前的元素。因此查到的下标一定小于 i，天然保证两个位置不同。

若先存当前元素，再查询，[3, 2, 4]、目标 6 就会暴露问题：处理第一个 3 时可能找到刚存入的自己，错误返回 [0, 0]。

先查后存不会漏掉 [3, 3]。第一个 3 查不到补数后入表；第二个 3 正好能查到它。禁止的是同一位置重复使用，不是相同数值出现两次。

为什么不会漏解？

设有效答案下标为 a < b。处理到 b 时，位置 a 的数值已经入表，所以查询补数一定可以命中。

如果这个数值后来又出现过，映射可能被更新为另一个更靠后的下标，但该下标仍然小于 b，数值也相同，因此依然能组成合法配对。保存每个值的一个历史下标就足够。

seen.get() 返回 Integer，不存在时是 null；下标 0 是正常结果，不能把它当成“没有找到”。代码先检查非空，再由 Java 自动拆箱放入返回数组。

复杂度和边界

  • 时间复杂度：哈希操作平均为 O(1)，整体期望 O(n)；不是对任意哈希冲突情况都承诺严格线性。
  • 额外空间：最多保存线性数量的不同数值，为 O(n)。
  • 重复值和零：[3, 3]、目标 6，以及 [0, 0]、目标 0，都需要两个不同下标。
  • 负数：补数计算不依赖正负，[-3, 4, 3]、目标 0 可返回 [0, 2]。
  • 最短合法数组：长度为 2 时同样适用。空数组、null、无解输入不在原题保证内；通用接口需要另行约定处理方式。

数值范围也要确认。若元素和目标值均在 [-10^9, 10^9] 内，补数在 [-2×10^9, 2×10^9] 内，Java 的 int 可以容纳。若接口允许任意 int 输入，就不能沿用这个安全前提：应使用 long need = (long) target - nums[i]，并配合 Map<Long, Integer>，避免减法溢出造成错误匹配。

面试时忘记怎么办

先写出最朴素的枚举：固定 i，寻找另一个数。然后问自己：“每次内层循环到底在找什么？”答案就是 target - nums[i]。

接着把内层扫描换成查询表，只记录已经走过的位置。最后用 [3, 2, 4]、目标 6 手推第一轮，就能重新推导出“先查后存”，不必硬背顺序。

可以这样讲清正确性：“循环开始时，表里都是历史元素，所以命中后不会使用同一位置；任何答案在处理其较晚下标时，都能找到较早的配对值。”再补上期望时间 O(n)、空间 O(n)。

一句话总结

把配对问题变成补数查询，再用“只存历史元素”同时保证效率和下标合法性。
