让智能体读文件、装依赖、调用接口，效率上来了，风险也跟着进入真实环境。NVIDIA 开源的 OpenShell 做的不是另一个聊天助手，而是智能体运行时：用策略限制它能接触的文件、进程和网络。它出现在今天的 GitHub 日榜，适合正在把自动化从演示搬到真实项目的开发者关注。

📌 这个项目是干什么的

  • 给已有智能体提供隔离沙箱，不替代模型或编程助手。
  • 通过网关管理沙箱，由边界外的监督进程检查网络请求、按规则注入服务凭据。
  • 面向需要运行编码助手、管理工具权限的开发者和平台团队。

🔍 为什么值得关注

关键区别是把约束放在运行环境，而不是只在提示词里要求“不要乱来”。文件访问由内核机制限制，网络请求必须经过策略检查；服务凭据不直接交给沙箱里的智能体。

另一个值得借鉴的设计是权限增量审批。官方示例中，访问未允许的目标会被拒绝并形成规则提案，网关先检查新增风险，再交给人审核。相比一开始开放全部网络，更容易看清任务究竟需要哪些权限。

🧪 谁适合试，怎么开始

先核对仓库中的支持矩阵，再按 README 安装命令行工具。创建最小沙箱的命令是：

openshell sandbox create --name demo

注意，默认镜像只有最小 Ubuntu 环境，没有预装智能体。接着看官方“运行第一个智能体”示例：配置 OpenRouter 服务凭据，选用包含 OpenCode 的镜像，再创建绑定服务的沙箱。

第一轮只放入测试项目，故意让它访问一个未授权地址，观察拒绝记录和规则提案。验收重点不是回答是否流畅，而是越界请求能否被挡住、放行是否足够窄。这是建议的试用路径，并非本文已完成的部署实测。

⚠️ 使用提醒

项目采用 Apache-2.0 许可证，但外部模型、镜像和服务仍有各自条款。Linux、苹果芯片 Mac 和实验性的 Windows WSL 2 支持条件不同，不能只看系统名称就判断可用。

沙箱也不等于业务安全证明：错误批准权限、挂载敏感目录，仍会扩大风险。先用假数据和低权限密钥验证，再考虑接入真实任务。
